FP32 FOC Multi-Motor HLS Design

Target library area: xf_motorcontrol/L1. Target device used for QoR: VCK190, xcvc1902-vsva2197-2MP-e-S, 5 ns clock.

Summary

The FP32 FOC design is layered into a golden algorithm core, an HLS stream wrapper, and a testcase top. Multi-motor support is implemented as a shared compute datapath with a per-motor context array. Each input sample carries a sideband motor-id stream, so the wrapper updates ctx[FOC_MOTOR_ID] and returns the selected id with the voltage command.

NUM_MOTORS=1 degenerates to the existing single-motor implementation and preserves the current QoR. NUM_MOTORS=64 reuses the same FOC compute and adds context-indexing overhead without replicating 64 FOC datapaths.

Dynamic Streaming Interfaces

Dynamic data is transferred through AXI4-Stream ports. The current multi-motor design uses an explicit sideband input id stream and an output id stream. This avoids relying on implicit round-robin ordering and lets downstream logic verify that each voltage command belongs to the expected motor.

QoR and Validation Results

Both configurations were validated with Vitis HLS 2026.2 on VCK190 at a 5 ns clock. The loop is intentionally not pipelined in this version, so throughput is approximately equal to the loop iteration latency.

Configuration CSIM Slack Loop Iteration Latency Approx. Per-Sample Time DSP BRAM FF LUT
Legacy ap_fixed Pass, legacy test 0.05 ns 33 cycles, II=5 50 ns throughput at 10 ns clock 43 2 6207 10442
NUM_MOTORS=1 Pass, 0 errors 0.05 ns 142 cycles 710 ns 35 0 9273 13957
NUM_MOTORS=64 Pass, 0 errors 0.05 ns 165 cycles 825 ns 23 0 9834 12142

The 64-motor configuration increases the single-sample iteration latency by 23 cycles, from 710 ns to 825 ns at 5 ns. This is a modest increase for storing independent context for 64 motors while keeping a single shared FOC compute instance.

Legacy ap_fixed Design Reference

The legacy IP is implemented by hls_foc_periodic_ap_fixed and hls_foc_oneSample_ap_fixed under L1/tests/IP_FOC/src, with the core template in L1/include/hw/foc.hpp. It uses fixed-point stream types for current and voltage commands, and AXI4-Lite integer registers that encode the FOC configuration and status values.

Implemented Legacy IP_FOC_Multiple Variant

The legacy ap_fixed IP now keeps the existing IP_FOC public signatures intact and adds context-aware variants in L1/include/hw/foc.hpp. The original foc_core_ap_fixed remains as a compatibility wrapper around one static context, while new multi-motor code calls the context-aware core directly.

FOC_MOTOR_ID uses natural binary motor IDs. IDs in 0 .. NUM_MOTORS-1 update the selected context and emit the computed voltage commands. Invalid IDs are not remapped; they skip context update, emit safe zero voltage commands, and return the original ID on FOC_MOTOR_ID_out.

Scalability Notes

The legacy fixed-point multi-motor top shares one FOC datapath and stores only per-motor control state. At 10 ns, the synthesized stream loop accepts one tagged sample every 200 ns for NUM_MOTORS=1 and every 270 ns for NUM_MOTORS=64. Servicing all 64 motor slots once therefore takes about 17.3 us, or roughly 57.9 kHz per motor when every slot is active once per round.

The 64-context design adds about 1.2k FF and 663 LUT over the single-context multi-motor top while keeping BRAM and DSP unchanged. Higher throughput would require reducing context/status dependencies, banking/partitioning selected context state, or instantiating multiple shared FOC engines.
